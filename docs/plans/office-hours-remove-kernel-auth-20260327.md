## Problem Statement
User goal is to remove kernel-layer authorization logic from Sandboxie and move toward a clean, reviewable upstream-ready implementation path.

## What Makes This Cool
- Convert a historically entangled authorization path into a cleaner architecture boundary.
- Make code easier to audit and maintain by eliminating dead/legacy licensing paths.
- Align kernel/service/GUI behavior to avoid split-brain policy outcomes.

## Constraints
- This is a high-risk area (`Sandboxie/core/drv/`), so isolation/security behavior must not regress.
- User selected a full-clean direction, but also selected staged/safe execution.
- Target audience is upstream/long-term maintainers, so reviewability and rollback are mandatory.

## Scope Guardrails
In scope:
- Authorization entitlement checks and license-gating paths across `drv/svc/gui`.
- Compatibility shims required to keep behavior stable during staged migration.
- Regression tests for security invariants and compatibility.

Out of scope:
- Refactors unrelated to auth retirement (naming/style-only churn).
- New product features.
- UI redesign beyond removing/neutralizing auth entry points.

## Glossary (Boundary Definition)
- Authorization logic: product entitlement/license gates that decide whether a feature is permitted for business reasons.
- Security policy checks: sandbox isolation, token restrictions, privilege boundaries, IPC/file/registry enforcement.
- Rule: if removing a branch can broaden sandbox privileges or weaken containment, classify as security policy and keep.
- Rule: if a branch only blocks feature usage due to entitlement state, classify as authorization and retire.

## Premises
1. The task is to remove product authorization logic, not weaken security boundaries (sandbox isolation, token restrictions, permission checks).
2. Changes must be reviewable, reversible, and regression-verifiable instead of one-shot large edits.
3. Kernel-side cleanup must stay consistent with service/GUI layers, otherwise behavior divergence and maintenance debt increase.

## Approaches Considered
### Approach A: Minimal Viable (Smallest Diff)
Summary: Make kernel auth decisions always-allow while keeping existing interfaces and config keys.
Effort: M
Risk: Low-Med
Pros:
- Smallest immediate blast radius
- Fastest to compile and smoke test
- Straightforward rollback
Cons:
- Leaves legacy structure behind
- Not a true full cleanup
- May defer debt to follow-up work
Reuses: Existing call chains and interfaces unchanged.

### Approach B: Ideal Architecture (Chosen)
Summary: Three-stage cleanup:
1) retire kernel authorization decisions behind compatibility shell,
2) remove or neutralize service/GUI authorization entry points consistently,
3) delete dead code and add regression checks + migration notes.
Effort: L
Risk: Med
Pros:
- End-to-end consistency across drv/svc/gui
- Strongest fit for upstream review
- Lowest long-term maintenance cost
Cons:
- Cross-module coordination required
- Longer execution cycle
- Needs explicit regression gates
Reuses: Existing module boundaries and current test/build workflows.

### Approach C: Creative Lateral (Feature-Flagged Decommission)
Summary: Introduce a decommission switch first, run 1-2 cycles with auth disabled, then physically remove code.
Effort: M-L
Risk: Low
Pros:
- Risk-controlled migration
- Supports branch parallelism
- Easier staged validation
Cons:
- Transitional complexity
- Temporary config burden
- Delays full cleanup
Reuses: Existing configuration and version migration mechanisms.

## Recommended Approach
Choose Approach B because it matches the declared goals: full cleanup, upstream-grade reviewability, and long-term maintainability. Use staged milestones and explicit regression gates between each layer.

Decision matrix (weighted):
- Maintainability 40%: A=5, B=9, C=7
- Safety 35%: A=7, B=8, C=8
- Delivery 25%: A=9, B=6, C=7

## Success Criteria
- Kernel authorization-specific branches are removed or neutralized without changing sandbox isolation semantics.
- Service and GUI no longer expose conflicting authorization behaviors.
- Build passes for affected solutions and basic runtime smoke tests succeed.
- A reviewer can map each stage to clear rollback and verification steps.

Mandatory security regression gates:
- Isolation invariants: file/registry/IPC redirection and access constraints remain unchanged.
- Token invariants: no privilege broadening for sandboxed processes.
- Negative tests: previously blocked security-sensitive operations remain blocked.
- Compatibility invariants: existing non-auth workflows behave the same before/after.

Test execution ownership and evidence:
| Gate | Test Method | Owner | Evidence |

| Compatibility invariants | Smoke-test common non-auth user workflows in GUI/service | QA/maintainer | Smoke checklist + screenshots/logs |

## PR Strategy (locked)

- Commit 1: Kernel retirement shell + invariant gates.
- Commit 2: Service/GUI alignment.
- Commit 3: Dead-code and config cleanup + migration notes.
- Rollback policy: if a gate fails in commit N, revert commit N only; do not proceed to N+1.
